The canonical BASIL source is now github.com/launchnlp/BASIL (2nd release, 2022) — that's the one you want, not the older marshallwhiteorg/emnlp19-media-bias repo, which is superseded but still references the correct citation. Use the launchnlp one.
Here's how I'd shape the first week or two. The crucial early move is to not run SHAP first. Classification metrics on BASIL are cheap, fast, and they determine the framing of everything downstream. SHAP runs are expensive enough that you want to know the lay of the land before you invest in them.
Phase 1 (1–2 days): get the data and read it by hand. Clone the launchnlp repo. BASIL is article-level with annotated spans, not sentence-level binary like BABE — each span carries a bias type (lexical vs informational) and a target entity. Before writing any code, read 20–30 annotated articles end to end. This is the step people skip and regret, because the label-alignment decision you make next is load-bearing for the whole comparison, and you can't make it well from the README alone.
Phase 2 (1–2 days): build the BABE-compatible view. You need to convert BASIL into a sentence-level binary classification task that your existing pipeline can consume. Standard recipe: split each article into sentences (spaCy is fine), mark any sentence containing ≥1 bias span as biased=1, others as 0. Critically, keep the bias_type metadata as a separate column — lexical, informational, or none. That's the column that lets you make a claim the original paper structurally cannot make: whether the two models' SHAP patterns differ across bias types. Don't throw it away during conversion.
A few preprocessing decisions to nail down explicitly and document, because reviewers will ask:

Sentences with both lexical and informational spans: label as biased, but log both types so you can stratify later.
Quoted material (BASIL keeps quotation marks on quoted biased sentences): decide whether to include or exclude. BABE doesn't have this distinction, so including them is the cleaner default, but flag it as a known scheme mismatch in the paper.
Class balance: check it. If BASIL ends up wildly more imbalanced than BABE's test split, your precision/recall numbers will be hard to compare directly. Report base rates for both.

Phase 3 (1 day): zero-shot classification, no SHAP yet. Run both HF checkpoints (himel7/bias-detector and mediabiasgroup/DA-RoBERTa-BABE-FT) on the BASIL sentences using the same 256-token preprocessing as your original Section 3.1. Produce a table: accuracy, precision, recall, F1 for each model, plus the same metrics broken down by bias type (lexical-only sentences, informational-only sentences). This single table is the first publishable artifact of the revision — it answers Reviewer cpFy's generalization question directly, and it tells you which way the paper has to be reframed.
Phase 4: decide before scaling up. Three things to look at:

If DA-RoBERTa-BABE-FT's precision advantage holds on BASIL, your "architectural and training choices critically affect deployment suitability" claim suddenly has out-of-distribution evidence, which is much stronger.
If both models score well on lexical-bias sentences but collapse on informational-bias ones, that's a finding, not a setback — it directly grounds Reviewer pfuu's "no definition of bias" critique in the BASIL typology. You'd reframe the paper's bias definition around this contrast.
If both models collapse entirely, that's the "interpretability findings don't transfer" reframing the revision plan mentions. Less flashy, still publishable, but you'd want to know now rather than after a week of SHAP runs.

Only after this phase do you port the SHAP pipeline. The pipeline itself should be a near-drop-in; the only thing to verify is that your word-boundary detection (Section 3.3 in the paper, plus the Appendix A heuristics) still behaves on BASIL's text, which has more quotation marks and proper-noun-heavy political content than BABE.
On MBIC as a secondary: I'd hold it as a backup rather than do both up front. BASIL's bias typology is the higher-leverage addition because it gives you a new axis of analysis. MBIC mostly adds volume and topical diversity on the same binary scheme, which is useful but less interesting. If you finish BASIL with time to spare in the ARR cycle, add MBIC; if BASIL surfaces something interesting that needs a third dataset to nail down, add it then.
One thing worth deciding before you start writing any code: do you want to fine-tune either model on BASIL, or strictly evaluate zero-shot? The revision plan implies zero-shot ("since they're BABE-finetuned"), which is the right call — fine-tuning on BASIL would let the models learn BASIL's specific quirks and muddy the cross-dataset comparison. But state this explicitly in the methodology section, because it's a defensible choice that's not the obvious one.
